# Architecture

Modular monolith. No microservices, no Kubernetes for the MVP.

```
frontend/   Next.js (App Router, TS, Tailwind, shadcn/ui)  ── calls ──┐
mcp-server/ Python MCP server (stdio) for Claude / Claude Code ──────┤
                                                                      ▼
backend/    Django + DRF  (auth, projects, credits, research API)
              │  enqueue
              ▼
            Celery workers (Redis broker)
              ├── research: providers fan-out → normalize → dedupe
              └── analysis: classify → cluster → competitors → score → distribution → report
              │
            PostgreSQL (all structured data)   S3-compatible storage (exports)
```

## Provider interface
```python
class ResearchProvider(Protocol):
    key: str                       # "web_search", "hackernews", ...
    def availability(self) -> Availability   # AVAILABLE | LIMITED | REQUIRES_CONNECTION | UNAVAILABLE
    def search(self, query: ResearchQueryIn, budget: Budget) -> list[RawResult]
    def normalize(self, raw: RawResult) -> EvidenceIn
```
One provider failing marks the job `PARTIALLY_COMPLETED`, never `FAILED`, unless all fail.

## Research pipeline (Week 2)
- **Drafting (free, 0 credits):** `POST /projects/{id}/interpret` and `/keywords/generate` call `research/ai/client.py::complete_json` (Anthropic SDK, structured outputs, jsonschema-validated, one retry). Output is stored apart from the founder's input (`IdeaDefinition.ai_interpretation`, `ResearchQuery.ai_generated`); cost goes on `UsageTransaction` with 0 credits. Throttle scope `ai`.
- **Launch:** `POST /research/jobs` snapshots `ResearchConfig` (sources, depth, queries, exclude terms, evidence/competitor URLs) onto the job; credits are spent in the same transaction.
- **Run:** stages `idea_analysis → web_research → community_research → evidence_analysis → competitor_analysis → report`. Providers declare a `stage`; URL providers (`user_urls`, `competitor_pages`) read the snapshot's URL lists through `providers/fetch.py` (public IPs only, robots.txt, 2 MB, 10 s). Query providers go through a 7-day `SearchCache`. Coverage per provider: `COMPLETED | FAILED | UNAVAILABLE | SKIPPED` (SKIPPED = nothing to read, doesn't make a job partial).
- Dev without Redis: `CELERY_TASK_ALWAYS_EAGER=True` runs the job inline.

## Job states
`DRAFT → PENDING → RUNNING → COMPLETED | PARTIALLY_COMPLETED | FAILED | CANCELLED`
Each stage writes a `JobStage` row so the progress screen shows real status (no fake percentages).

## Auth
- **Browser:** django-allauth headless (`/_allauth/browser/v1/...`): email + password signup/login, Google OAuth, email verification. Session cookie + CSRF (`X-CSRFToken`).
- The Next.js app proxies `/api/*` and `/_allauth/*` to Django (`BACKEND_URL`), so cookies are first-party and no tokens live in JS storage.
- **MCP / scripts:** `Authorization: Api-Key vm_...` (keys managed at `/api/api-keys`).
- Signup grants `FREE_SIGNUP_CREDITS` once, only after the email is verified (`email_confirmed`, or a Google signup with a verified email). The `signup_grant:<user id>` idempotency key on `UsageTransaction` prevents double grants.
- API keys can read but cannot manage keys or change the account (a leaked key can't mint replacements).
- DRF throttling (`THROTTLE_ANON`/`THROTTLE_USER`) on the `CACHE_URL` cache. **Deploy note:** Next's rewrite proxy does not send `X-Forwarded-For`, so put a real reverse proxy in front that does and set `ALLAUTH_TRUSTED_PROXY_COUNT` before relying on per-IP auth rate limits.
- Google redirect URI: `{FRONTEND_ORIGIN}/accounts/google/login/callback/` (proxied; Django builds it from `X-Forwarded-Host`). "Continue with Google" only shows when `GOOGLE_CLIENT_ID`/`SECRET` are set.

## MCP server (`mcp-server/`)
Thin client over the REST API, authenticated with a user API key (`VALIDME_API_KEY`). Tools:
`validate_idea`, `get_research_status`, `get_report`, `search_evidence`, `list_competitors`, `suggest_channels`.
Set `VALIDME_MOCK=1` to return fixture data for local development without the backend.

## AI usage
LLM calls live only in `backend/research/ai/` behind one interface (`complete_json(prompt, schema)`), so the model provider (Claude or OpenAI) is a config switch. Every LLM output is validated against a schema before saving.

## Cost control
Per job: `search_cost + llm_input_cost + llm_output_cost`, stored on `UsageTransaction`. Cache search results 7 days by `(provider, normalized_query)`. Depth = hard budget of queries/results/tokens.

## Report (Week 4)
- Built by `reports/services.py::build_report` as the last job stage and stored as a `Report.content` snapshot, so a report never changes after it's generated.
- **Competitors** (`reports/competitors.py`): listed ones are profiled from the fetched page (`SourceSnapshot`); a price is kept only if it appears verbatim on that page, with its URL and retrieval date, otherwise pricing is "unavailable". Competitors mentioned in evidence must be named in the cited excerpts.
- **Scoring** (`reports/scoring.py`): deterministic, from evidence counts. A dimension without evidence is "not scored", its weight is excluded and `scored_weight` says how much of the model was scored. Confidence = min(volume, diversity, recency); low confidence never recommends "build". Since Week 15 (`score_v2`) the founder's Lab experiments are blended in as tier-1 evidence (see "Close the loop").
- Market size stays "unavailable" until a sourced calculation exists. Unclassified evidence is never presented as a finding.

## Audience, distribution and history (Week 5)
- `reports/distribution.py` is deterministic. A channel is **Researched** only when classified evidence (pain, workaround, feature request, alternative seeking, pricing objection, buying intent) was published there; competitor pages never count. Other channels are **Hypothesis** with no evidence count.
- Audience segments are the founder's (or AI-suggested, labelled) segments matched to that evidence by word; needs come from AI themes that share records.
- Audience accessibility (10%) is now scored from researched channels: distinct places and threads. No places → not scored.
- The first-10 plan is a checklist the founder runs by hand. Nothing is sent for them (rule 8).
- A completed project can re-run (`POST /research/jobs`, new idempotency key); each run adds a `Report`, so history is the list of snapshots. A failed re-run keeps the project `COMPLETED` so earlier reports stay reachable.
- PDF export is the browser's print dialog on a print layout of all sections; Markdown export is server-side (`reports/export.py`).

## Billing, limits, recovery and analytics (Week 6)
- **Payments:** Lemon Squeezy is the merchant of record (tax/VAT, invoices, refunds). `POST /billing/checkout` creates a pending `Purchase` and returns a hosted checkout URL; no payment script runs on our pages. Credits are granted only by the signed `order_created` webhook, after checking the purchase id, the user, the pack's variant and test/live mode. `provider_order_id` is unique and the ledger key `purchase:<order>` is idempotent, so retries never double-credit. `order_refunded` takes back the pack's unspent credits once.
- **Packs and prices** live in config (`CREDIT_PACKS`, `SUBSCRIPTION_PLANS`) and in Lemon Squeezy, which decides what is charged. The decided list prices are mirrored for display in `frontend/src/content/pricing.ts` (pricing page, and the in-app fallback before payments are live); in the app the provider's own label always wins. Without configuration, buying is closed.
- **Plan limits** (`billing/plans.py`, `PLAN_LIMITS`): "free" (no paid pack) runs Quick only; everyone has caps on running jobs and launches per day. Checked at launch under a lock on the user row; 403 `plan_depth`, 429 `too_many_running` / `daily_limit`, nothing charged.
- **Job recovery:** a job that fails (crash, or no source could be searched) is refunded once (`job_refund:<job>`). `recover_stuck_jobs` runs every 5 minutes via Celery beat (and `manage.py recover_jobs`): PENDING > 15 min or RUNNING > 45 min → FAILED with a visible reason, refunded, project released.
- **Errors:** API paths return the JSON error envelope for unmatched URLs and crashes (`config/errors.py`); messages never include exception details. Logs go to stdout; httpx request logs are off (their URLs can carry API keys).
- **Analytics:** first-party only (`analytics.AnalyticsEvent`): server events for research/report/purchase milestones; a short whitelist of client events via `POST /analytics/events`. No cookies, IP or user agent stored; query strings stripped; nothing sent when the browser signals Global Privacy Control or Do Not Track.
- **Free-plan evidence preview:** `EVIDENCE_PREVIEW_LIMIT` (10) most relevant originals per project are browsable in `GET /evidence` (and the MCP `search_evidence`); search, filters, duplicates, detail and save stay inside that set (`evidence/views.py::preview_ids`), and the list response carries `preview {limited, available, total}`. It's a browsing limit, not secrecy: reports and exports always include every record they cite (rule 1).
- **Refund edge cases:** partial refunds take back `floor(credits × refunded/total)`, cumulative and idempotent per level; a refund delivered before the paid event is recorded on the purchase (found via our purchase id) and the paid event then grants only the unrefunded part; a refund for an unlinked order returns 409 so the provider retries. `status: refunded` always counts as full.
- **Hardening (security review):** API keys stop working for deactivated users and write `last_used_at` at most every 5 minutes; throttles key on the proxy-appended IP (`DRF_NUM_PROXIES`); anonymous analytics has a global daily cap and per-event prop keys (slug values only); webhook signature compare is byte-safe; `Idempotency-Key` ≤ 80 chars; Celery soft/hard time limits sit below the stuck-job timeout and job status changes are conditional, so a recovered (refunded) job is never completed or restarted by a late worker; `LEMONSQUEEZY_TEST_MODE` defaults to DEBUG.

## Monitoring engine (Week 8)
- `monitoring` app: **Watch** (URL, cadence daily/weekly, next_run_at, validators, last hash, status) → **Observation** (stored only when the visible text changed, ≤ 20k chars) → **Change** (deterministic diff: prices added/removed, text blocks added/removed; significance high for price changes).
- **Cycle:** `claim_due` leases due watches with `select_for_update(skip_locked)` (one query + one update, whatever the count); `check_watch` takes a per-host slot (`cache.add`, Redis in prod), fetches through the SSRF-safe fetcher with `If-None-Match` / `If-Modified-Since`, hashes the normalized text and stops there when nothing changed. Errors back off (1h, 2h, 4h…) and pause the watch after 5 in a row. Retention keeps the last 10 observations plus any a Change references.
- **Runs locally** with `python manage.py monitor` (one cycle) or `--loop --interval 60`; in production Celery beat calls `monitoring.tasks.run_due_watches` every 5 minutes and fans out one task per watch.
- No AI yet (Week 9 adds summaries of the diff only, labelled).
- **Hardening (security review):** the diff is a linear multiset difference (no difflib), so a hostile page can't stall a worker, and it runs before any transaction opens; Celery check tasks have their own 60/90 s limits. Claims carry a lease token (a duplicate or stale task can't run a check twice) and take at most one watch per host per cycle. Politeness slots are per host **and** per resolved IP, so wildcard DNS can't multiply requests to one victim. ETag/Last-Modified are stored only when printable ASCII; any unexpected error counts as a failed check (backoff/pause). Changes are capped per watch (`MONITORING_KEEP_CHANGES`). "Check now" claims its cooldown atomically and runs on the task queue; create/check/from-report share the `monitoring` throttle. MCP API keys are read-only on monitoring.
- **Production requires a shared cache:** with `DEBUG` off the app refuses to start if `CACHE_URL` is the per-process locmem cache (throttles, the analytics cap and monitoring politeness would silently multiply).

## Change intelligence & alerts (Week 9)
- **AI summary of a change** (`monitoring/summarize.py`, prompt `change_summary_v1`): input is the deterministic diff only (prices added/removed, up to 20 text blocks), escaped so page text can't close the `<diff>` tag; stored in `Change.ai_summary` / `ai_watch_for` apart from the factual `summary` and always labelled. Dropped if it mentions a price not in the diff. Low-significance changes aren't summarised; per-account daily cap `MONITORING_AI_DAILY` (free 10, paid 10, founder 100, pro 300); cost on the ledger with 0 credits.
- **Notifications** (`notifications` app): one per change (deduped by `source`), notice first then summary, each isolated so neither fails the check; links must be internal app paths; inbox capped at 200 per user. Bell polls once a minute while visible.
- **Entitlements v1** (`PLAN_LIMITS`): see Week 10 for the plan table. Enforced on create / from-report / cadence change (user row locked); after a downgrade the oldest watches up to the limit keep running and the rest wait (shown on the page). `/me` returns `monitoring {max_watches, cadences, used}`.


## Digest, new competitors and subscriptions (Week 10)
- **Email provider** (`EMAIL_PROVIDER`): `console` locally; `smtp` for a Gmail account with an app password (fine for testing, ~500/day); `resend` (`mailer/backends.py`, HTTPS API, logs status only). Switching is config only.
- **Weekly digest** (`mailer/digest.py`, Monday 08:00 via beat, or `manage.py send_digests [--user] [--dry-run]`): last 7 days of high/medium changes (max 15) and new candidates (max 10); every item links to its change or candidate in the app, AI summaries labelled; nothing is sent in a quiet week. Text + HTML (autoescaped, no images or tracking). `DigestLog` is unique per user per ISO week, so a retry or a second worker can't send twice.
- **Recipients:** active users with a watch whose address is **verified** (allauth `EmailAddress`), digest on, not bounced.
- **Unsubscribe:** signed token (`django.core.signing`, own salt, user id only) in the link and in `List-Unsubscribe` + `List-Unsubscribe-Post` (one-click). Opening the link changes nothing (mail scanners prefetch links): `/unsubscribed` asks and POSTs; it's noindex and `Referrer-Policy: no-referrer`. **Bounces/complaints** from Resend's Svix-signed webhook mark the address bounced and turn the digest off; re-enabling in Settings clears it.
- **New-competitor detection** (`monitoring/candidates.py`, Monday 05:00; accept/dismiss share the `monitoring` throttle): the project's enabled queries (competitor-gap first, max 3) against Hacker News "Show HN" posts from the last 60 days (public Algolia API, no AI). Skips known domains (competitors, watched pages, earlier candidates) and hosting/code/social sites; at most 5 new per run, one in-app notice per project per week. The founder accepts (→ Watch, same URL validation and plan caps) or dismisses; nothing is watched automatically.
- **Subscriptions:** Lemon Squeezy `subscription_*` webhooks upsert a `Subscription` by provider id. On first sight the user comes from our checkout's `custom_data`, which carries an HMAC (`checkout_sig`, SECRET_KEY) of user + plan, so a hand-edited buy link can't attach a subscription to someone else. Unknown variants are ignored, test/live mode must match, and an event older than the stored `provider_updated_at` is ignored (retries can't revive an expired plan). `plan_for`: an entitling subscription (`on_trial`, `active`, `past_due`, or `cancelled` until `ends_at`) → its plan; else a paid pack → `paid`; else `free`. `subscription_payment_success` grants `monthly_credits` (×12 for yearly) once per invoice (`sub_credits:<invoice>`), only for `billing_reason` initial/renewal with a non-zero total (prorated plan-change invoices grant nothing); `subscription_payment_refunded` takes back the refunded share of that grant, capped at the balance, once per level; `order_*` events for subscription orders are ignored; an invoice that arrives before its subscription returns 409 so the provider retries. Plan changes and cancellation happen in the provider's customer portal.

## Opportunity Radar (Week 11)
- **Signals** (`radar.Signal`) come only from data we already store, by fixed rules (`radar/generators.py`); thresholds are conservative (a missed signal beats a fabricated one). A **source** is a distinct author on a site (the page when the author is unknown), so one thread or one person is never "many sources"; a **site** is a host.
  - **Complaint theme** (opportunity): a theme from the latest analysis in a complaint category (pain point, pricing objection, workaround, seeking alternatives) with ≥ 5 records, ≥ 3 sources on ≥ 2 sites and mean relevance ≥ 0.5 (scored records only). Keyed by the normalised theme name; a renamed theme sharing ≥ 50% of its evidence with an earlier signal isn't new.
  - **Discussion trend** (trend): publish dates of our own collected evidence. Windows end at the last research run's completion (not today, so a frozen sample isn't read as going quiet): ≥ 6 records in the 30 days before it, ≥ 3 in the 90 days before that, a ratio ≥ 2, the same source/site/relevance floor, and some evidence older than the baseline. Pain point and buying intent first; "all discussion" only when neither fired. Worded as "in the records we collected", never as a market measurement. At most one per group per month.
  - **Competitor change** (risk): a high-significance change on a watched page, created the moment monitoring detects it (no second notice: the change already sent one).
  - **New competitor** (risk): a candidate the founder accepted (watched). A match alone never becomes a signal.
- **Scores are rules, not AI:** relevance = mean classifier relevance; impact from sources and records; for monitoring signals both are fixed by kind (0.9/0.7 report vs. added page, 0.8 pricing / 0.5 content; 0.6/0.5 new competitor) and the UI says so. Confidence for evidence signals: high = ≥ 3 sources on ≥ 2 sites from ≥ 2 platforms with ≥ 60% of records from the last 6 months (undated count as not recent), medium = ≥ 3 sources on ≥ 2 sites; the counts are stored in `facts.confidence_basis` and shown. A page diff we read is high; a confirmed new competitor medium. Rank = relevance × impact.
- **AI rationale** (`radar/rationale.py`, prompt `signal_rationale_v1`): input is the idea, the signal's facts and up to 5 excerpts of its own evidence, each in its own tag, all declared data and escaped. Output `ai_rationale` + `ai_action` is stored apart and labelled. It is dropped when it uses any number (compared with its unit: "$9bn", "17%", "6x") that isn't one of the signal's computed counts or prices, or a magnitude word ("doubled", "millions"). A discarded or failed attempt is marked in `ai_version` and never retried. Only the 3 strongest open signals per run, one run per project at a time (cache lock), counted against the same daily AI allowance as change summaries (`MONITORING_AI_DAILY`).
- **Statuses:** new → seen (shown on screen) → acted / dismissed; feedback useful / not useful (also on acted/dismissed ones). Unique per project + key, so a dismissed signal doesn't come back.
- **Revalidation and score snapshots** (`radar.ScoreSnapshot`, with `scoring_version`): every research report stores a snapshot; `revalidate_all` (Monday 06:00, before the 08:00 digest) and "Check now" (`radar_refresh` throttle 6/hour, one at a time per project) re-score stored evidence with the same `score_project` (no network, no AI) and store a point when the result moved or at least weekly. Skipped while a research run is active (themes and competitors are being rebuilt). "Not scored" is stored as null, never 0.
- **Digest:** up to 5 open signals found that week with their factual basis line (theme names marked as AI-written), labelled AI view and a link to `/projects/{id}/radar?signal=…`.

## Distribution data v2 (Week 12)
- **GitHub issues** (`research/providers/github_issues.py`): a normal evidence provider (community research stage). Public issues from the last 2 years with at least one interaction, via the REST search API; the query text is stripped of `key:value` qualifiers and boolean operators so it can't widen the search; issue markdown and template comments are removed before excerpting; after a 403/429 the provider pauses for a minute (recorded as a provider failure, so the job is PARTIALLY_COMPLETED); LIMITED without `GITHUB_TOKEN`. In distribution a repository is its own channel only with ≥ 2 distinct relevant issues (mean relevance ≥ 0.5); one-offs are grouped as "GitHub issues".
- **YouTube** (`distribution/youtube.py`): on request only. Up to 3 of the project's queries (customer-acquisition and problem-discovery first) → `search.list` (videos, last 12 months) → `channels.list`. Stored per project in `YouTubeChannel` with `expires_at` = read + 29 days, so with the daily purge (`purge_expired_youtube`, 03:30) nothing is kept past 30 days; a refresh replaces the rows (unless channel details couldn't be read, then the old rows stay and the look-up is FAILED); the API never serves expired rows. Titles are HTML-unescaped; `subscribers_hidden` distinguishes "hidden by the channel" from "not given". Figures are YouTube's own (subscribers — `None` when hidden — and video count), activity is the latest matching video, relevance is ours ("found by N of your searches") and labelled as such; nothing is combined into a score and nothing is copied into evidence or reports. Guards: researched projects only; 6-hour cooldown per project after any look-up that spent quota; per-account daily budget `YOUTUBE_USER_DAILY_UNITS` (~4 look-ups) and global `YOUTUBE_DAILY_UNITS`, both counted on YouTube's quota day (midnight Pacific); the units are reserved on the `ProviderCall` before calling out; quota errors recorded as FAILED; the searches that ran are stored so the page can say "found by N of M searches".
- **Keyword demand** (`distribution/keywords.py`): DataForSEO Google Ads search volume (`/keywords_data/google_ads/search_volume/live`) + Labs keyword difficulty (`/dataforseo_labs/google/bulk_keyword_difficulty/live`). Keywords are the project's queries cleaned to ≤ 10 words / 80 chars, looked up as English searches; location from the founder's market (fallback United States, said in the UI). The allowance is reserved on the `ProviderCall` before paying; keywords with no figure are counted in the note. Cached 30 days per project; per-plan monthly allowance `KEYWORD_LOOKUPS_MONTHLY` (free 10, paid 10, founder 100, pro 300) and global `DATAFORSEO_MONTHLY_BUDGET_USD`; cost on the ledger (0 credits) and in `ProviderCall`. A missing figure stays null ("Unavailable"); a failed difficulty call keeps the volumes and marks the look-up LIMITED.
- **Coverage (rule 4):** every look-up writes a `ProviderCall` (OK / LIMITED / FAILED / REQUIRES_CONNECTION / SKIPPED with a user-safe note); the page shows the last one per provider. `ProviderCall.project` is SET_NULL, so deleting a project doesn't erase the usage allowances are counted from. Refresh runs one at a time per account (lock above the worst-case run time).
- **Page** `/projects/[id]/customers` ("Where to find your customers"): researched/hypothesis channels from the latest report, YouTube channels (credited to YouTube, with the read date and deletion date), search demand table (volume, CPC, ad competition, difficulty, 12-month line from the raw monthly figures), and the first-10 plan with cited evidence. Terms and Privacy carry the YouTube statements.

## Validation Lab 1: landing page + waitlist (Week 13)
- **Origin isolation (ADR-6):** `lab.middleware.LabHostMiddleware` (first in the stack) routes requests whose Host is `LAB_HOST` to `lab.public_urls` — only `/p/{slug}`, `/p/{slug}/join` and `robots.txt` exist there; the API, admin and auth don't. Founder content is never served from the app origin. Every Lab response gets a CSP with no scripts (`default-src 'none'`, `style-src 'nonce-…'`, `script-src 'none'` unless Turnstile is on, `form-action 'self'`, `frame-ancestors 'none'`, `base-uri 'none'`), `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer`, COOP/CORP same-origin, `X-Frame-Options: DENY`, `Cache-Control: no-store`, and **all cookies are stripped**. Settings refuse to start with `SESSION_COOKIE_DOMAIN`/`CSRF_COOKIE_DOMAIN` set, or (DEBUG off) with `LAB_HOST` equal to the app's host or no `LAB_ENCRYPTION_KEYS`. Locally the app is `localhost:3000` and pages are `127.0.0.1:8000` (different origins, no shared cookies); production should use a separate domain (best) or `pages.<domain>`.
- **Pages are structured blocks** (`lab/blocks.py`, JSON Schema): hero, problem, benefits (≤ 6), pricing (≤ 3, always followed by a fixed "Not available yet… nothing is charged" note), FAQ (≤ 8), waitlist; ≤ 12 blocks, plain text with length limits, control/bidi characters stripped, and no links, web or email addresses anywhere (refused on save). Templates autoescape; `linebreaks` is the only formatting. Fixed footer on every page: an independent founder's early test page, the product may not exist yet, links to privacy, deletion request and "report this page".
- **Publish rules:** verified email, a hero, a waitlist, a title, a slug (3–48 chars, lowercase, reserved words like `admin`, `login`, `billing`, `support` refused). Unpublished pages 404. The slug can't change while live. Pages per account by plan (`LAB_PAGES`: free 1, paid 1, founder 3, pro 10), checked under a lock on the user row.
- **Waitlist form** (plain HTML POST, no JavaScript): no CSRF cookie (no sessions on this origin) — instead a signed, page-bound form token at least 3 seconds and at most 2 hours old; honeypot field (silently "succeeds"); rate limits per hashed IP+page (5/h), per hashed IP (20/h) and per page (300/h), counted only in the cache; optional Turnstile (server-verified). Duplicates get exactly the same response as new sign-ups. Consent checkbox with fixed wording (`lab-consent-v1`, includes the retention period); the version and time are stored.
- **Personal data:** `WaitlistSignup.email_encrypted` (Fernet via MultiFernet, keys in `LAB_ENCRYPTION_KEYS`, rotatable; dev derives one from SECRET_KEY), `email_hash` (HMAC, separate key) only for dedupe; no IP, user agent or cookie. `expires_at` = join + the page's retention (30–365 days, default 180); `purge_expired_signups` deletes daily at 03:45. Founders see decrypted emails in the app, export CSV (formula injection neutralised) and delete one or all.
- **Analytics:** `LabDailyStat` per page per day — views (GET without `joined`/`error`, bots skipped by user agent) and sign-ups. Conversion = sign-ups ÷ views, null without views. No cookies, so repeat visitors can't be told apart (said in the UI).
- **AI copy** (`lab/suggest.py`, prompt `lab_copy_v1`): from the idea, audience and theme names; refused if it contains any digit or number word, links, or testimonial/award/"trusted by" claims; labelled in the editor; counts against the shared daily AI allowance.
- **Editor UI:** `/projects/[id]/lab` (list, new page from the idea's name) and `/projects/[id]/lab/[pageId]` (title, web address with availability check, retention, block forms with reorder/remove/add, AI suggestion panel, sticky save/publish bar, live preview with the same consent text, results and waitlist panels). Linked from the report's Project tools.

## Validation Lab 2: surveys and price tests (Week 14)
- **Surveys** (`lab/surveys.py`, JSON Schema like blocks): ≤ 12 questions, each `{id q1–q99, type single|multi|scale|text, prompt ≤ 200, help, options 2–8 (choice only, distinct), low/high labels (scale 1–5), required, assumption_id}`; plain text, no links; `assumption_id` must be one of the project's assumptions (rule 2: the assumption stays the founder's, answers are a separate result). Once a survey has answers, its structure (ids, types, options, order) and `ask_email` can't change; wording can. Plan cap `LAB_SURVEYS` (free 1, paid 1, founder 3, pro 10).
- **Public survey** (`lab/public_surveys.py`, `/s/{slug}`): same guards as the waitlist (signed survey-bound token ≥ 3 s, honeypot, per hashed IP+survey 5/h and per IP 20/h, per survey 500/h counted only for valid answers, optional Turnstile). Choices are stored as option numbers (anything not offered is ignored); typed answers as one Fernet token; the optional email encrypted + HMAC (only to find it for data requests). Consent `lab-survey-consent-v1` includes retention and, with the email field, that anonymous answers can't be found later. Errors re-render the form with the person's answers (from the POST, not stored). Closed surveys show a notice. Daily purge at 03:50 (`purge_expired_responses`).
- **Price test:** a pricing block may carry `test_variants` (B, C; A = `items`), only one such block per page. Without cookies the variant is `sha256(hashed IP | page | day) % n` (stable for reloads; can differ across days/networks, said in the UI); only that variant's prices are in the HTML. The form token carries the variant (signed), so sign-ups are attributed to what was seen; "Choose <plan>" is a POST to `/p/{slug}/choose` (token ≥ 1 s old), counted once per client per page per day, then `?picked=` shows "It isn't available yet and nothing is charged". `LabVariantStat` per test version, variant and day (views, clicks, signups); `WaitlistSignup.variant`. **Test versions:** `price_test()` fingerprints the names, prices and periods of all variants (`test_key`); changing, adding or removing a variant starts a new version. Results show only the current version next to its prices and report earlier versions' totals separately (`previous`), so counts are never shown against prices nobody saw; a token from an older version doesn't attribute its sign-up or click. Public numeric inputs go through `lab.surveys.small_int` (ASCII digits, ≤ 3 digits), so "²" or huge numbers can't cause errors.
- **Results and sample size:** every count comes with `sample_note(n)` — none / too_small (< 10) / small (< 30) / ok — and the worst-case 95% margin `1.96·√(0.25/n)`. Rates are null without a denominator. Variant comparisons use a two-proportion z-test and say `not_enough_data` unless both variants have ≥ 100 views, `no_clear_difference` below |z| 1.96, otherwise which is higher "among the people you reached". No combined score.
- **Respondent data requests** (`lab/data_requests.py`, linked from every Lab footer): email + copy/delete. Guards: form token, honeypot, 5/h per hashed IP, 300/h site-wide, optional Turnstile. The answer is always the same, and the email is queued (encrypted in the queue) whether or not anything matches; the task (`ignore_result`, returns nothing, logs no address, swallows SMTP errors) emails a signed single-use link (`h` = email HMAC, `k` = kind, random `j`; copy 1 h, delete 24 h) only when there's a match, capped per address and kind at 1/h and 3/day (counted only for emails sent, so a stranger can't block the owner). Settings refuse `CELERY_TASK_ALWAYS_EAGER` with DEBUG off, because an inline task would make timing reveal whether an address is held. Keep `t=` out of access logs (proxy config) even though links are single-use. The link's GET shows a confirm button; POST burns `j` (a second use says "already used") and shows the copy (page/survey titles, dates, answers in words) or deletes every sign-up and survey response with that HMAC, logs a `DataRequest` (counts only, no address) and creates a `DataRequestNotice` per affected project so the founder also cleans any CSV they exported (shown on the Lab page until marked read). Founders can still delete one or all from the app, and export CSV.
- **AI questions** (`lab/suggest.py::suggest_questions`, prompt `lab_survey_v1`): input is the idea and up to 8 open assumptions, each in its own tag, escaped. Output keeps only questions about given assumption ids that pass the schema, link check and a leading/PII-wording filter; ids are reassigned; labelled in the editor; counted against the shared AI allowance.
- **UI:** Lab list adds Surveys and deletion notices; survey editor `/projects/[id]/lab/surveys/[surveyId]` (survey settings, question cards, AI panel, sticky bar with Publish/Close/Reopen/Unpublish/Delete, preview with the saved consent text, Results with bars and sample warnings, Answers with export/delete). Page editor: variants inside the pricing block, price-test table and comparisons in Results.

## Close the loop: experiments, verdicts, scoped keys (Week 15)
- **Experiments as tier-1 evidence** (`lab/experiments.py`, ADR-7): demand = waitlist sign-ups ÷ views pooled over the project's pages that have been live; willingness to pay = "Choose" presses ÷ views of each page's current price-test version. A rate counts only from `MIN_VIEWS` (30) views and is scored from the **lower bound of its 95% Wilson interval** against a 10% target (`min(100, low / 0.10 × 100)`), so small samples score low; the targets are our rule of thumb, said in the report. Confidence: high ≥ 300 views, medium ≥ 100. Successes are capped at views (views are counted once per network a day, so a shared office can sign up more often than it "viewed"; said in the explanation). Days with more than 5× the median daily views (with ≥ 7 days of data) are left out and listed. Presses on free options ("Free", "$0", "0 €") aren't counted as willingness to pay. Counts are as they happened, including people since removed. `reports.scoring.with_experiment` blends a counted result into its dimension at 60% (or scores it alone, keeping research's own explanation of why it had nothing) and keeps `research_score`, `research_confidence`, `research_explanation` and `experiment` (with the Lab rows it came from) on the dimension; the blended confidence is the **weaker** of the two; overall confidence stays research-only (said in the rules note). A too-small result is only mentioned, with how many more views it needs. Both results come from the same visitors, which the rules note says. `SCORING_VERSION = "score_v2"`; new reports and Radar re-scores (`rescore`) both pass the experiments, so score history shows their effect; report content records `experiments_used` and `experiment_rules`. No experiments → a "run a test page" tip first in "what would change".
- **Assumptions from surveys** (`lab/verdicts.py`): a survey question linked to an assumption may say which answers support it (`support_options` for choice questions — not all of them — or `support_min` 2–5 on the scale; typed answers are never judged). Per question, with ≥ 10 answers: supported if the 95% Wilson interval of the supporting share is entirely above 50%, contradicted if entirely below, else inconclusive; several questions combine (any support and none contradict → supported, and the reverse; a mix → inconclusive). Counts are "answers", not people: the same email counts once (latest answer), anonymous answers can't be told apart (the form limits answers per network). A rule set, or a question reworded, after answers arrived (`Survey.late_rules`) makes the verdict **advisory**: shown, never applied to the status. AI-drafted questions carry `drafted_by: "ai"` and the verdict says so. Each reference records the first and last answer time. Stored on `Assumption.auto_status / auto_basis / auto_refs / auto_at`, apart from the founder's `status`. While `status_locked` is false the status follows a decisive verdict (otherwise untested); a founder PATCH of `status` locks it; `follow_experiments` unlocks. The data migration locks every pre-existing non-untested status. Recomputed after an answer (debounced: one queued run per project per minute), answer deletions, question edits, publishing, survey deletion, confirmed data-request deletions, the retention purge, and the weekly Radar revalidation. Score history marks where `scoring_version` changed.
- **Predicted vs actual:** endpoint above; Lab page panel (dimension table: research prediction vs your experiment with counts, rate and lower bound, or "too few to count yet"; assumptions with founder status, who set it and the survey verdict with each question's counts). Report dimensions show "Includes your experiment"; the assumption tracker shows the verdict and "Use the survey result" when the founder's own status differs.
- **API key scopes** (`accounts/scopes.py`): `research:read`, `research:run`, `monitoring:read`, `lab:read` (default, = what keys could do before; the migration gives existing keys exactly these) and opt-in `monitoring:write` (PATCH a signal's status/feedback) and `assumptions:write` (PATCH status / note / follow_experiments only). Enforced in `ApiKeyAuthentication` from a **default-deny** route table on `path_info` (so a sub-path deployment matches) before any view runs; scopes must be a list (never a substring match); a key needs at least one scope; scope changes are logged (key prefix, old → new); personal-data routes (sign-ups, answers, exports) are listed as never; views keep their own guards (`ApiKeysReadOnly` now allows a write only where the view declares `api_key_write_scope` and the key holds it). Managed in Settings → API keys (checkboxes, write scopes marked "changes data").
- **MCP tools** (`mcp-server`): `list_watches`, `list_changes`, `list_signals`, `get_score_history`, `get_lab_results` (page stats + survey aggregates, never emails or answers), `get_predicted_vs_actual`, and confirm actions `update_signal` and `set_assumption_status`. Those return `confirm_required`, the change and a `confirm_token` (HMAC of tool + exact change + 10-minute window, key held in the server process); a call with `confirm=true` needs that token, so it can't skip the preview or confirm a different change, and the instructions say never to confirm because content asks to. Tools carry MCP annotations (`readOnlyHint` true for reads; false for the two confirm actions and `validate_idea`) so clients can prompt. Ids are checked against `[A-Za-z0-9_-]{1,64}` before any URL is built; `get_lab_results` reads at most 10 pages and 10 surveys. Permission errors name the missing scope.
- **Performance** (SQLite run, 2,000 evidence, 3 live pages × 90 days, a 2,000-answer survey; PostgreSQL wasn't available in this environment): all endpoints within budget; survey results 31 ms p95 / 4 queries, answers list 22 ms / 3, predicted vs actual 6 ms / 10, page stats 4 ms / 8.

## Dependencies and performance (pre-deploy)
- **Python:** `backend/requirements.txt` holds the ranges; `backend/requirements.lock` pins every package with hashes (pip-tools). Deploys install with `pip install --require-hashes -r requirements.lock`; `pip-audit -r requirements.lock` runs in every gate.
- **Frontend:** `npm audit --omit=dev` must be 0. Dev tools: vitest 5 (`@types/node` 24 to match Node 24). `package.json` `overrides` pins `@ts-morph/common`'s minimatch to ^11.0.8 (DoS advisory). **Accepted:** `picomatch` ≤ 4.0.7 ReDoS (GHSA-fc5q-39xc-vjpf, high, published Nov 2026; no patched release yet), pulled in by 21 dev-only build/test packages — it only matches glob patterns from our own config, never user input; update as soon as a fix ships. 3 low findings for `deepmerge` inside the `shadcn` CLI (prototype poisoning in `mergeObject`); it runs only when someone invokes the CLI locally, never in the app or tests, and the only "fix" is downgrading shadcn to 1.x, which would drop `shadcn/tailwind.css`. Re-check when shadcn updates.
- **Performance check:** `python manage.py perf_check` seeds one founder (2 projects, N evidence records, clusters, a built report, 15 watches, 120 changes, 5 candidates, 60 notifications, 80 ledger rows) inside a transaction that is always rolled back, switches off outside calls and throttles, then times 22 read endpoints: p50/p95 over `--requests` runs plus the query count of one request. Budgets p95 ≤ 250 ms, ≤ 20 queries; `--strict` fails on a breach, `--json` saves results. Baseline (2026-11-16, local PostgreSQL, 2,000 evidence, 30 requests): every endpoint ≤ 66 ms p95 and ≤ 6 queries; slowest are evidence clusters (65 ms), facets and filtered evidence search (~48 ms). Week 11 adds signals (≈ 23 ms p95, 4 queries) and score history (≈ 5 ms, 2 queries).
